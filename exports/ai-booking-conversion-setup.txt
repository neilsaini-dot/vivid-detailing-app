AI BOOKINGS — VIVID DETAILING

Production setup (one time):
1. Open the existing Supabase project's SQL Editor.
2. Run the LATEST scripts/migrate-ai-booking-conversions.sql, even if you
   ran the previous version. It adds/updates only ai_booking_conversions.
   Existing booking data, GHL mappings and prices are unchanged.
   Railway must have GHL_PRIVATE_TOKEN and GHL_LOCATION_ID configured.
   The token needs calendars/events.readonly and calendars/events.write.
3. Open Admin > AI Bookings.

Day-to-day use:
1. Open Review & Convert on an imported ceramic or detailing special.
2. Fill in the customer's name/phone and correct the vehicle information.
   Email, vehicle year/descriptions, and notes can be left blank.
3. Save details stores the edits without sending any automations.
4. Convert to booking runs in this exact order:
   a. Create a NEW app-owned Google event in contact@vividpei.com using
      the normal native app format.
   b. DELETE the original GHL appointment through its API. It is not
      cancelled. If deletion fails, keep going and flag manual cleanup.
   c. Send the usual booking_confirmed webhook.
   d. Mark converted, retaining the existing app booking ID.
5. The row moves to Converted history. Open booking uses the usual
   inspection, pickup, completion, and customer portal flow.

Pricing:
Changing vehicle type recalculates the applicable special price, while
preserving existing extras and staff price overrides. Ceramic stays at
$995 before HST. No client-supplied total is accepted during conversion.

Retries:
- A successful conversion cannot re-send the booking-confirmed webhook.
- If Google Calendar creation fails, GHL is not deleted and confirmation
  is not sent. Resume conversion retries unfinished steps only.
- If the GHL delete fails, the booking still converts. A visible warning
  includes the original GHL appointment ID for manual DELETION, not cancellation.
- If webhook delivery is uncertain, check the booking-confirmed workflow's
  execution history in GHL using the booking ID. In the review sheet,
  confirm you checked GHL, then mark whether it actually delivered.
- Never mark "not delivered" without checking; that could resend an automation.
- Interrupted in-progress requests have a two-minute safety wait before
  staff can record verification.

Appointment ownership:
Before conversion, reschedule in GHL. Once converted, reschedule/cancel in
the usual app Bookings tab. The original GHL mapping is retained for audit;
late GHL notifications cannot cancel or change the app-owned booking.

Bot-only queue:
Only explicit chat/voice-bot origins are included. Google/app origins and
unknown origins are excluded. GHL creator metadata is checked through the API.
If your bot's API appointments report only a generic "api" creator, add
"bookingOrigin": "chat_bot" OR "bookingOrigin": "voice_bot" to the authenticated
bot-specific intake workflow's webhook body. Never add this marker to a generic
appointment-created or Google-sync workflow. Explicit Google/app creator
metadata overrides a supplied bot marker.

Live dummy test (required before treating deletion as message-silent):
Book via the chat or voice bot using a designated test contact with controlled
phone/email. Convert that booking, verify the original GHL appointment is gone,
check contact@ for only the new app event, and inspect the test contact's
SMS/email inbox and GHL workflow/message history for cancellation notifications.
An HTTP success or mocked test does not by itself prove notification silence.

Without the production SQL setup, AI Bookings explicitly shows a setup
message. Existing native booking pages and GHL imports continue unchanged.
